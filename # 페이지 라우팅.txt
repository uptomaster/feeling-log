# 페이지 라우팅
사용자 - 브라우저 - 서버 간 요청과 응답

브라우저에서 /blog를 요청하면 서버는 그에 맞는 페이지를 찾아서
브라우저에게 반환한다.
이 반환받은 html을 브라우저에 띄우게 된다. 

이러한 방식의 여러 개의 페이지를 갖는 어플리케이션 => MPA라고 부른다.
MPA는 동작 방식이 직관적이어서 많은 곳에서 활용된다.

서버 측에서 미리 만들고 보내주는(렌더링) 방식을 서버 사이드 렌더링이라고한다.

단 MPA와 서버 사이드 렌더링은 다르다.

하지만 리액트는 이런 MPA방식을 따르지 않는다.. 페이지이동을 빠르게 처리하기 힘듦.
MPA방식에서 유저가 페이지에 접속해있을때 링크나 버튼을 통해 페이지를 이동하려 하면
서버는 실시간으로 찾거나 만들어서 반환한다.
이떄 브라우저는 원래 페이지를 제거하고 새로운 페이지를 렌더링하며 페이지 이동이 완료된다.
이동할 때마다 지우고 새롭게 처음부터 렌더링하는 것 => 새로고침과 같음

대법원 사이트를 보면 페이지 이동할때마다 살짝씩 페이지가 깜빡이며 새로고침되는걸 볼 수 있다.
원래 페이지를 완전히 제거하고 새로운 페이지를 새로고침하는 방식이 바로 MPA인데,
원본을 전부 제거하고 새로 그리는건 비효율적이라는 의미이다.

따라서 리액트는 MPA방식을 따르지 않고, SPA방식을 따른다.
페이지 이동을 매끄럽고 효율적으로 처리하며 다수의 사용자 트래픽이 몰려도 부하를 줄인다.
sigle page application, SPA방식의 리액트 웹서버는 페이지를 단 한개 index.html만 가진다.
기타 유틸이나 컴포넌트 들은 JS Files로 존재한다.

웹 페이지에 브라우저가 접속을 요청하면 항상 index.html을 보내준다.
이 파일은 리액트의 빈 껍데기 역할을 한다.(아무것도 렌더링 안되고 script태그)

그럼 브라우저는 이 빈 껍데기를 먼저 렌더링한다.
이때 리액트 웹서버는 후속으로 우리가 만든 리액트 컴포넌트나 기능이 작성된 js파일들을 하나로 묶어서
브라우저에게 추가로 전달해준다. 이렇게 묶어주는 행위를 번들링이라고한다.
이 번들링된 파일을 Bundle JS File이라 부른다.
묶는 행위는 Vite에 의해 번들링되어 브라우저에게 추가로 전달된다.

그럼 이 전달된 번들 파일을 직접 브라우저가 가장 먼저 실행하며 컴포넌트들을 화면에 렌더링하며
우리가 작성한 컴포넌트, 기능들이 렌더링된다.

이러한 방식ㅇ르 컴포넌트 렌더링, 클라이언트 사이드 렌더링이라고 한다.
앞서 살펴본 서버 사이드 렌더링과는 반대 개념이다.

그리고 사실상 Bundle JS File을 React App이라 부른다.

다시 정리하면, 리액트는 서버가 직접 페이지를 모두 가지고있는 MPA방식을 따르지 않고,
기본 틀 역할을 하는 index.html과 JS Files로 구성하는 SPA방식을 따르며 브라우저의 접속 요청이 들어오면
기본 틀인 index.html을 전달하고, 번들링된 JS 파일들을 후속으로 전달하고,
브라우저에서는 이 파일들을 직접 실행하며 렌더링하게 된다. 
그리고 이때 번들링된 JS파일들은 리액트로 작성한 모든 파일이 담겨있어 React App이라 부른다.
